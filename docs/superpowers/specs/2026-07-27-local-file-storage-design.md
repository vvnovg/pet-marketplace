# Локальное файловое хранилище

Дата: 2026-07-27
Статус: утверждён

## Задача

`LocalFileStorageService` — заглушка. `store()` логирует «not implemented yet» и
возвращает `""`, `getPublicUrl()` возвращает `""`, `retrieve()` бросает
`UnsupportedOperationException`. При этом `storage.provider: local` выставлен и в
`application.yml`, и в `application-prod.yml`, а `@ConditionalOnProperty` объявлен с
`matchIfMissing = true` — то есть это активная реализация во всех окружениях.

Следствие: каждый путь загрузки отвечает успехом, ничего не сохранив.
`ProfileService.uploadAvatar` записывает `avatarUrl = ""` и возвращает 200, а страница
`/dashboard/profile` показывает «Аватар обновлён» — при том что файла нет. Та же
заглушка обслуживает фотографии объявлений (`ListingService`) и вложения в сообщения
(`MessageService`).

Надо, чтобы загруженный файл действительно сохранялся и открывался в браузере.

## Ограничение, определяющее архитектуру

В продакшене бэкенд закрыт файрволом: порт `8080` не принимается на внешнем интерфейсе,
публичен только фронтенд на `3000` (см. `README.md`, раздел Deploy). Изображения при этом
грузит сам браузер через `<img src>`, а не клиентский JS, — то есть URL из базы должен
разрешаться относительно origin фронтенда.

Поэтому файлы отдаются через уже существующий проксирующий маршрут фронтенда
`/api/proxy/*`. Новых публичных портов не появляется, модель «браузер общается только с
фронтендом» сохраняется.

## Поток данных

```
браузер  <img src="/api/proxy/files/avatars/{userId}/{uuid}.png">
   ↓
Next.js  /api/proxy/[...path]  (proxy-handler.ts)
   ↓
бэкенд   GET /api/v1/files/{bucket}/{objectKey}
   ↓
диск     {storage.local.base-path}/{bucket}/{objectKey}
```

Том `app-uploads` уже смонтирован в `/app/uploads`, и `STORAGE_LOCAL_PATH: /app/uploads`
уже задан в `docker-compose.yml`. Персистентность между пересборками обеспечена, менять
compose не нужно.

## `LocalFileStorageService`

Реализуются все четыре метода интерфейса `FileStorageService`; сигнатуры не меняются.

| Метод | Поведение |
|---|---|
| `store` | Создаёт родительские каталоги, пишет поток в `{base-path}/{bucket}/{objectKey}`, возвращает результат `getPublicUrl(bucket, objectKey)`. Существующий файл перезаписывается. |
| `retrieve` | Возвращает поток файла. Если файла нет — `ResourceNotFoundException`. |
| `delete` | `Files.deleteIfExists`. Отсутствие файла — не ошибка. |
| `getPublicUrl` | `{storage.public-base-path}/{bucket}/{objectKey}` |

`storage.public-base-path` — новое свойство со значением по умолчанию `/api/proxy/files`,
переопределяемое переменной окружения. Так префикс маршрутизации фронтенда остаётся
конфигурацией, а не зашитой в код бэкенда строкой.

**Защита от обхода пути.** `objectKey` в GET-эндпоинте приходит из URL, поэтому целевой
путь нормализуется (`Path.normalize()`) и обязан оставаться внутри `base-path`; иначе —
отказ. Проверка применяется во всех четырёх методах, а не только в чтении.

Ошибки ввода-вывода оборачиваются в `BusinessException` — так же, как это уже делают
вызывающие сервисы при чтении `MultipartFile`.

## `FileController`

Новый контроллер, `GET /files/{bucket}/**`. Отдаёт `Resource` поверх
`fileStorageService.retrieve(...)`.

- Content-Type выводится из имени файла через `MediaTypeFactory.getMediaType(...)`,
  фолбэк — `application/octet-stream`. Отдельно тип не хранится: расширение сохраняется
  в `objectKey`, чего для изображений достаточно.
- Ключи содержат UUID и потому неизменяемы — ответ отдаётся с длительным
  `Cache-Control`.
- Несуществующий ключ → 404 через `ResourceNotFoundException` (уже маппится в
  `GlobalExceptionHandler`).

## Права доступа

В `SecurityConfig`, до `anyRequest().authenticated()`:

| Путь | Доступ | Почему |
|---|---|---|
| `/files/avatars/**` | `permitAll` | Публичные профили открыты анонимам |
| `/files/images/**` | `permitAll` | Каталог объявлений открыт анонимам |
| `/files/messages/**` | `authenticated` | Личная переписка |

Прокси подставляет bearer из httpOnly-куки, поэтому вложения в чате откроются, когда
чат будет реализован. Проверка «запросивший — участник диалога» не делается: она
потребовала бы поиска сообщения по URL вложения и запроса в БД на каждую картинку.
Аутентификации достаточно, пока чат не построен; ужесточить можно вместе с ним.

## Правка имени бакета

`ListingService.IMAGES_BUCKET` сейчас равен `"petmarketplace"` — это имя бакета MinIO,
а не смысловая категория. С ним публичный URL фотографии объявления выглядел бы как
`/files/petmarketplace/listings/...`, и правило доступа пришлось бы вешать на сегмент
`petmarketplace`.

Константа меняется на `"images"`. Мигрировать нечего: реальных загрузок никогда не
происходило (хранилище не работало), а демо-сид хранит пути на статику фронтенда
(`/animals/*.jpg`) и не затрагивается.

Ключи аватаров и вложений дублируют имя бакета (`bucket = "avatars"`, `objectKey =
"avatars/{userId}/..."` → `/files/avatars/avatars/{userId}/...`). Это остаётся как есть:
исправление затронуло бы три сервиса ради вида URL.

## Правка прокси на фронтенде

`src/lib/api/proxy-handler.ts` на обоих путях возврата делает `await upstream.text()`.
Это декодирует тело как UTF-8 и разрушает бинарные данные — изображения через прокси
приходят битыми. Заменяется на `arrayBuffer()`.

Заголовок `content-length` продолжает вырезаться `sanitizeHeaders`; Next выставит его
сам.

Это единственное изменение во фронтенд-репозитории.

## `MinioFileStorageService`

Не реализуется. Но `store` и `getPublicUrl` начинают бросать
`UnsupportedOperationException` вместо возврата `""`.

Именно тихий `""` и породил исходный баг: API отвечал 200, вызывающий код записывал
пустую строку, а пользователь видел успех при отсутствии файла. Заглушка, падающая
громко, такого не допустит.

## Мёртвая ветка у вызывающих

Все три сервиса написаны так:

```java
storedUrl = fileStorageService.store(BUCKET, objectKey, ...);
if (!StringUtils.hasText(storedUrl)) {
    storedUrl = fileStorageService.getPublicUrl(BUCKET, objectKey);
}
```

После того как `store` начнёт возвращать непустой URL, второй вызов станет
недостижимым. Ветка остаётся: она безвредна и служит подстраховкой для реализаций,
которые вернут пустую строку.

## Тесты

**Бэкенд**, интеграционные, в `src/test/java/com/petmarketplace/infrastructure/storage/`:

- `store` кладёт файл по ожидаемому пути и возвращает ожидаемый URL;
- `retrieve` отдаёт ровно те байты, что были записаны;
- `delete` удаляет файл и не падает на отсутствующем;
- `objectKey` с `..` отвергается во всех четырёх методах;
- `store` перезаписывает существующий файл.

**Контроллер**, в `src/test/java/com/petmarketplace/application/file/`:

- публичный аватар отдаётся анониму с 200 и корректным Content-Type;
- `/files/messages/**` без токена → 401, с токеном → 200;
- неизвестный ключ → 404.

**Сквозной:** `POST /users/me/avatar` → `GET` по возвращённому URL отдаёт тот же файл.
Это тот сценарий, который сейчас молча не работает.

**Фронтенд:** тест, что прокси возвращает бинарный ответ неповреждённым (сравнение
байтов, а не строк).

pnpm build && pnpm exec playwright test` во фронтенде.
